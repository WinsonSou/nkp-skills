Delete the Bootstrap Cluster
Remove the temporary bootstrap cluster after you delete the managed workload cluster.
About this task
After you move workload resources to a bootstrap cluster and successfully delete the managed cluster, you
no longer need the bootstrap cluster and can delete it.
To delete the bootstrap cluster, follow this step:
Procedure
•
Delete the bootstrap cluster using the following command:
nkp delete bootstrap --kubeconfig $HOME/.kube/config
Sample output:
# Deleting bootstrap cluster

When you provision Kubernetes clusters with the Nutanix Kubernetes Platform (NKP) vSphere provider,
specific roles and permissions are required for NKP to provide appropriate access to resources.
About this task
Roles in vSphere act as policy statements for objects in the vSphere inventory. You can assign roles to
users and propagate object assignments to child resources. In small vSphere environments, assigning a

Base OS Image for NKP in vCenter
Create a base OS image in vCenter for use when building vSphere VM templates for NKP clusters.
Creating a base OS image from DVD ISOs is a one-time process in vCenter. Nutanix Image Builder (NIB)
uses this base image to create VM templates for Kubernetes nodes. For more information, see VMware
image documentation.
Base OS Image Configuration
For vSphere, SSH_USERNAME defines the username, and authentication uses SSH_PASSWORD or
SSH_PRIVATE_KEY_FILE. This user requires administrator privileges unless you provide an overridden NIB
configuration for a custom user.
Consider the following when creating the base OS image:
•
Storage configuration: Customize disk partitions and avoid configuring a swap partition.
•
Network configuration: Enable network access so NIB can download and install packages.
•
Red Hat registration: Required for RHEL to configure repositories and install packages.
•
Software selection: Use Minimal Install.
•
Install packages from operating system package managers using versions aligned to the OS major
version.
Disk Size
For each cluster that you create from this image, define root file system disk size based on NKP minimum
resource requirements and your organization's minimum storage requirements.
NKP creates clusters with a default disk size of 80 GB.
For clusters that use the default disk size, keep the base OS image root file system at exactly 80 GB
because the system does not reduce the root file system automatically at first boot.
For detailed image build steps, see Building a Custom Image with vSphere.

Loading the Registry
Load NKP air-gapped image bundles into your private registry and local runtime.
Procedure
1. Download the complete NKP air-gapped bundle for your release and extract the tar file:
tar -xzvf nkp-air-gapped-bundle_nkp-version_linux_amd64.tar.gz
2. Change to the extracted directory:
cd nkp-nkp-version
3. Set registry environment variables:
export REGISTRY_URL="https/http://registry-address:registry-port"
export REGISTRY_USERNAME=username
export REGISTRY_PASSWORD=password
4. If the registry uses a self-signed certificate, set the certificate authority file path:
export REGISTRY_CA=path-to-cacert-on-bastion
5. Load the NKP image bundle into your private registry:
nkp push bundle --bundle ./container-images/nkp-image-bundle-nkp-version.tar \
--to-registry=${REGISTRY_URL} \
--to-registry-username=${REGISTRY_USERNAME} \
--to-registry-password=${REGISTRY_PASSWORD}
6. Load the Kommander image bundle into your private registry:
nkp push bundle --bundle ./container-images/kommander-image-bundle-nkp-version.tar \
--to-registry=${REGISTRY_URL} \
--to-registry-username=${REGISTRY_USERNAME} \
--to-registry-password=${REGISTRY_PASSWORD}
7. On the bastion host, load the Konvoy bootstrap image into your local container runtime:
For Docker:
docker load -i konvoy-bootstrap-image-nkp-version.tar
For Podman:
podman load -i konvoy-bootstrap-image-nkp-version.tar
podman image tag konvoy-bootstrap:vnkp-version docker.io/mesosphere/konvoy-
bootstrap:vnkp-version

About this task
A self-managed cluster runs Cluster API resources and controllers on the same cluster they manage. The
process initializes a temporary bootstrap cluster locally, provisions cluster nodes in vSphere, and pivots
management components to the new cluster.
To create an NKP management cluster, follow these steps:
Procedure
1. Set a unique cluster name:
export CLUSTER_NAME=your-cluster-name
2. Export vCenter server credentials and connection details:
export VSPHERE_SERVER=vCenter-API-server-URL
export VSPHERE_USERNAME=vCenter-username
export VSPHERE_PASSWORD=vCenter-password
3. Create the vSphere cluster with the self-managed workflow:
nkp create cluster vsphere \
  --cluster-name ${CLUSTER_NAME} \
  --server ${VSPHERE_SERVER} \
  --data-center DATACENTER_NAME \
  --resource-pool RESOURCE_POOL_NAME \
  --data-store DATASTORE_NAME \
  --folder FOLDER_NAME \
  --network NETWORK_NAME \
  --control-plane-endpoint-host CONTROL_PLANE_VIP \
  --vm-template TEMPLATE_NAME \
  --ssh-public-key-file SSH_PUBLIC_KEY_FILE \
  --self-managed
(Optional) For air-gapped environments, append registry mirror parameters:
--registry-mirror-url=${REGISTRY_URL} \
--registry-mirror-username=${REGISTRY_USERNAME} \
--registry-mirror-password=${REGISTRY_PASSWORD}
4. Monitor and wait for control plane readiness:
kubectl wait --for=condition=ControlPlaneReady "clusters/${CLUSTER_NAME}" --
timeout=20m
5. Retrieve kubeconfig for the new management cluster:
nkp get kubeconfig -c ${CLUSTER_NAME} > ${CLUSTER_NAME}.conf
What to do next
To verify that control plane and worker nodes are ready, use the command kubectl get nodes.
