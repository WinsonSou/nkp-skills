AI Workload Scheduling
Use AI workload schedulers to apply gang scheduling, fair queueing, or advanced GPU-sharing policies to
AI workloads in NKP. Use a gang scheduler when distributed AI workloads require all worker pods to start
together. Gang scheduling avoids partial startup, stranded accelerator capacity, and unstable distributed
job initialization.
Use this guidance to select a scheduler:
•
Kueue: When you need queue-based admission and gang scheduling for distributed jobs.
•
Slurm Operator: When you need Slurm-oriented queue and job control for HPC-style workflows.
•
KAI Scheduler: When you need policy and queue-based behavior for shared GPU workload fairness.
For GPU workloads, you must first configure NVIDIA Operators, then enable the scheduler application.
You can validate the scheduler deployment by checking the application status in the NKP UI and the Helm
release readiness in the target workspace namespace. For more information, see GPU Management on
page 607.

Kueue for Gang Scheduling
Kueue is a job queueing and quota system that provides gang scheduling and queue-based admission
control for distributed AI workloads in Nutanix Kubernetes Platform (NKP).
Use Kueue in NKP when distributed AI jobs must start as a coordinated unit and consume quota-managed
resources. Kueue adds queue-based admission control on top of Kubernetes scheduling, so jobs wait until
the required resources are available rather than starting partially.
Gang scheduling means all required workload units (for example, worker pods in a distributed training
job) are admitted together. If cluster resources cannot satisfy the full request, Kueue keeps the workload
pending in the queue, and thus prevents the following:
•
Partial startup of distributed jobs
•
Stranded GPU allocations
•
Repeated retry loops from under-provisioned starts
Use these objects to control admission behavior:
•
Local queue: A namespaced queue that application teams use to submit workloads
•
Cluster queue: A cluster-scoped quota and policy pool that backs one or more local queues
Kueue checks workload requests against the cluster queue quota and policy. If quota is available, Kueue
admits the workload; if not, the workload remains queued.
Kueue and GPU Allocation
Kueue does not replace GPU device allocation. GPU Operators expose allocatable GPU resources, and
Kueue uses those resources in admission decisions.
This interaction model uses the following lifecycle:
•
Resource publication: The GPU Operator publishes the available GPU resources.
•
Admission evaluation: Kueue evaluates queue quota and workload requests.
•
Pod scheduling: Kubernetes schedules admitted pods onto eligible GPU nodes.
Note:  Configure node labels and tolerations to ensure deterministic GPU placement after admission.
Use Kueue when you need the following:
•
Coordinated start for distributed jobs
•
Queue fairness across teams
•
Explicit quota control per tenant or project

The following operational examples show how Kueue acts as a gatekeeper:

The job requires eight GPU-consuming workers. With default scheduling, some workers can start
while others wait, causing an unstable startup. With Kueue, admission waits until the quota can
satisfy all workers, then the job starts coherently.
Multi-Tenant AI Workspace
Team A and Team B share the same GPU cluster. The cluster queue enforces tenant quotas. The
local queue isolates team submissions. Kueue admission prevents one team from consuming all

•
Use TLS for all external inference paths.

Keep route definitions in version-controlled manifests and promote the manifests through staged
environments.
