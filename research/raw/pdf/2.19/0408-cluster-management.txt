Creating Nutanix Kubernetes® Platform (NKP) Clusters on Failure Domains
Nutanix Kubernetes® Platform (NKP) supports failure domains on Nutanix infrastructure and enables
you to configure failure domains based clusters using API. You can enable failure domains on both
management and managed clusters. Failure domains distribute control plane nodes across separate
infrastructure availability zones to ensure that the NKP cluster remains operational when failure domain
fails. The failure domain in Nutanix infrastructure directly maps to the Prism Element cluster and a set of
subnets associated with that cluster.
Use failure domains to achieve the following:
•
Higher availability of Kubernetes control plane: Creates three control plane VMs across three Prism
Element clusters.
•
Predetermined placement of worker node pools: Assigns each node pool to a specific Prism Element
cluster.
•
Reusable configuration: After you create a Nutanix failure domain object, you can reference it on any
cluster within that namespace.
Caution:  The persistent volumes are not portable across failure domains. If the Prism Element cluster
associated with the failure domain fails and cannot recover, NKP does not replicate the corresponding
storage volumes to Prism Element clusters associated with other failure domains.
Prerequisites
Before you create and apply failure domain objects to an NKP cluster, ensure that your infrastructure
meets the following requirements:

Attaching an existing AWS cluster requires that the cluster be fully configured and running. You must create

cluster-specific to and isolated from Kommander.

cert-manager functions as expected, you can ignore this failure. It will have no impact on the operation of
the cluster.

Cluster Attachment with Networking Restrictions
Configure the network-resrtricted cluster settings.
Need for a Secure Tunnel
When attaching a cluster to NKP, the Management cluster initiates an outbound connection to the cluster
you want to attach. This is not possible if the cluster you want to attach (Managed or Attached) has
networking restrictions and is not exposed, for example, because it is in a private network or its API is not
accessible from the same network as the Management cluster. This is what we call a network-restricted
cluster.
Figure 7: Network-restricted Cluster
Tunneled Attachment Workflow
NKP can create a secure tunnel to enable the attachment of clusters that are not directly reachable.
To create a secure tunnel, you must provide a configuration for the tunnel in the cluster you want to attach.
After you apply that configuration, the cluster you want to attach will establish a secure tunnel with the
Management cluster and make an attachment request.

Reasons For Setting Up a Custom Domain or Certificate.
Reasons for Using a Custom DNS Domain
NKP supports the customization of domains to allow you to use your own domain or hostname for your
services. For example, you can set up your NKP UI or any of your clusters to be accessible with your
custom domain name instead of the domain provided by default.

Reasons for Using a Custom Certificate
NKP’s default CA identity supports the encryption of data exchange and traffic (between your client and
your environment’s server). To configure an additional security layer that validates your environment’s
server authenticity, NKP supports configuring a custom certificate issued by a trusted Certificate Authority
either directly in a Secret or managed automatically using the ACME protocol (for example, Let’s Encrypt).
Changing the default certificate for any of your clusters can be helpful. For example, you can adapt it to
classify your NKP UI or any other type of service as trusted (when accessing a service through a browser).

operations. For information, see Cluster Operations Management on page 227. You can do this for
any cluster type in your environment.

scenarios, as these services require connection to the Internet for their setup. For air-gapped environments,
you can either use self-signed certificates issued by the cluster (the default configuration), or a certificate

Disconnecting or Deleting Clusters
Disconnect or delete a cluster.
About this task
When you attach a cluster that was not created with Kommander, you can later detach it. This does not
alter the cluster's running state but simply removes it from the NKP UI. User workloads, platform services,
and other Kubernetes resources are not cleaned up at detach.
Warning:  After successfully detaching the cluster, manually disconnect the attached cluster's Flux
installation from the management Git repository. Otherwise, changes to apps in the managed cluster's
workspace will still be reflected on the cluster you just detached. Ensure your nkp configuration references
the target cluster. You can do this by setting the KUBECONFIG environment variable to the appropriate
kubeconfig file location. For more information, see https://kubernetes.io/docs/tasks/access-
application-cluster/configure-access-multiple-clusters/. An alternative to initializing the KUBECONFIG
environment variable is to use the –kubeconfig=cluster_name.conf flag. Then, run kubectl -n
kommander-flux patch gitrepo management -p '{"spec":{"suspend":true}}' --type
merge to make the cluster's workloads not managed by Kommander, anymore.
If you created a managed cluster with NKP, it cannot be disconnected. The cluster must be deleted, and
completely removes the cluster along with all of its cloud infrastructure assets.
We recommend deleting a managed cluster through the NKP UI.
Warning:  If you delete the Management cluster, you can not use NKP to delete any Managed clusters
created by NKP. If you want to delete all clusters, ensure you delete all Managed clusters before finally
deleting the Management cluster.

IPAM Configuration Change Limitation
Changing the IP address management (IPAM) configuration on a running NKP cluster is an unsupported
change and disrupts existing workloads.
Nutanix Kubernetes Platform | Cluster Operations Management | 497

--- page 498 ---
Nutanix Kubernetes Platform (NKP) configures IPAM during cluster creation. Cilium and the Kubernetes
controller manager cannot reconcile IPAM changes on a running cluster, which causes cluster-wide
networking issues.
Warning:  Do not change the IPAM mode, Pod classless inter-domain routing (CIDR), or Service CIDR of an
existing, running NKP cluster.
Restriction
On a running NKP cluster, do not perform any of the following actions:
•
Change the Cilium IPAM mode. For example, changing from kubernetes to cluster-pool.
•
Modify the Pod CIDR block.
•
Modify the Service CIDR block.
•
Expand or shrink the existing Pod or Service CIDR range.
Impact
Any of the preceding changes result in the following outcomes on the cluster:
•
Immediate and persistent connectivity disruption for existing workloads.
•
Pods that fail to schedule or receive routable IP addresses.
•
Cluster networking that cannot be recovered by reverting the change.
Supported Resolution
To change the IPAM configuration, mode, Pod CIDR, or Service CIDR of an NKP cluster, provision a new
Kubernetes cluster with the required IPAM settings. Then, migrate your workloads to the new cluster.
For more information on creating a cluster with a custom Cilium configuration, see Creating a Nutanix
Cluster With Custom Cilium Configuration on page 726.
For more information on maximum transmission unit behavior for AHV clusters that use Cilium with overlay
networking, see Maximum Transmission Unit Configuration for AHV Clusters on page 711.

Stopping an NKP Cluster
Gracefully stop an NKP cluster.
Before you begin
•
Stop the applications and pods in the NKP cluster. This helps reduce the possibility of data corruption.
•
Take a backup of the Kubernetes cluster. For more information, see Velero Backup.
Note:
•
This procedure is applicable to all infrastructure providers. However, the example provided in
this topic is based on a Nutanix deployment.
•
Steps 2, 3, 4, and 5 are specific to Nutanix AHV environments. However, the other
infrastructure providers can also use similar steps to shutdown the NKP VMs.
•
If your NKP cluster uses an external DHCP server instead of Nutanix IPAM, do not use the
Guest Shutdown action. A guest shutdown might release the DHCP lease, and the VM can
restart with a different IP address. Kubernetes and Cluster API (CAPI) require persistent IP
addresses, so the Kubernetes node becomes unusable. Use the Power Off action instead,
and configure DHCP reservations for the cluster nodes or set the DHCP lease duration longer
than the planned downtime.

About this task
To shut down an NKP cluster, follow these steps:
Procedure
1. Pause remediation of the managed cluster on the management cluster:
kubectl patch cluster <clustername> -n <namespace> --type merge -p '{"spec":
{"paused": true}}'
This annotates the workload cluster to stop remediation.
2. In Prism Central UI, shut down the nodes.
a. Log in to Prism Central.
b. In the top-left corner, click the menu icon.
c. Select Compute  > VMs > Filters.
d. Select the Name checkbox, change the option to Starts with, and type the following:
nkp_cluster_name-
Where, nkp_cluster_name- is the name of the NKP cluster.

Replacing SSH Keys in a Nutanix Kubernetes Platform Cluster
You can replace SSH keys on existing Nutanix Kubernetes® Platform (NKP) clusters to comply with key
rotation policies or after an SSH key is compromised.
Before you begin
Ensure that your environment meets the following requirements before you replace SSH keys:
•
You have kubectl administrative access to the NKP management cluster.
•
You have privileges to edit Cluster API secrets and objects in the cluster namespace.
•
You have a new SSH public and private key pair.
The following steps use ~/.ssh/new-nkp-key as an example path for the new key pair. Replace this path with
the path and file name that you use.
About this task
NKP stores the cluster SSH key in a Kubernetes Secret. The secret name is typically CLUSTER_NAME-ssh-
key in the namespace where you deployed the cluster.
For newly provisioned nodes, updating the secret is sufficient for the nodes to use the new key during
provisioning. Cluster API does not automatically synchronize SSH keys to running nodes because cloud-
init runs only during the initial boot of a virtual machine. For existing nodes, you must append the new
public key to the authorized_keys file on each node. This requirement applies to all supported infrastructure
providers: AWS, Azure, GCP, vSphere, Nutanix AHV, and pre-provisioned (Metal).
Caution:  On pre-provisioned (metal) clusters, NKP uses the SSH private key in the secret to manage nodes
through Cluster API Runtime Extensions and Ansible. Append the new public key to authorized_keys on all
nodes before you update the secret, or immediately after you update it. Otherwise, NKP loses management
access.
To replace SSH keys in an existing cluster, follow these steps:
Procedure
1. Set the CLUSTER_NAME and NAMESPACE environment variables:
$ export CLUSTER_NAME=cluster-name
Nutanix Kubernetes Platform | Cluster Operations Management | 505

--- page 506 ---
$ export NAMESPACE=cluster-namespace
Replace cluster-name with the name of your cluster, and replace cluster-namespace with the
namespace where you deployed the cluster.
2. (Optional) Generate a new SSH key pair:
$ ssh-keygen -t ed25519 -f ~/.ssh/new-nkp-key -N "" -C "new-nkp-key"
The command creates an Ed25519 key pair. The -N "" flag sets an empty passphrase. If your security
policy requires a passphrase, omit -N "" or replace the empty value with your passphrase.
3. Back up the existing SSH secret:
$ kubectl get secret ${CLUSTER_NAME}-ssh-key -n ${NAMESPACE} -o yaml > backup-ssh-
secret.yaml
If the secret uses a different name, replace ${CLUSTER_NAME}-ssh-key with the secret name in your
cluster.
4. Inspect the backup file and confirm the secret data key names:
Open backup-ssh-secret.yaml and record the data key names in the existing secret. Preserve those
names when you update the secret.
Caution:  Inspect the existing SSH secret and preserve its current data key names when you update it.
Do not assume that the keys are ssh-privatekey, ssh-publickey, or id_rsa. If your deployment
documentation specifies a different SSH key procedure, follow that procedure.
5. Update the SSH secret with the new key pair:
$ kubectl create secret generic ${CLUSTER_NAME}-ssh-key -n ${NAMESPACE} \
  --from-file=ssh-privatekey=~/.ssh/new-nkp-key \
  --from-file=ssh-publickey=~/.ssh/new-nkp-key.pub \
  --dry-run=client -o yaml | kubectl apply -f -
The --dry-run=client -o yaml | kubectl apply -f - pattern updates the existing secret in place.
The ssh-privatekey and ssh-publickey values in this command are examples. Replace them with
the data key names from your backup file.
6. Append the new public key to the authorized_keys file on each existing node:
Set SSH_USER to the SSH user for your OS image. Common values include nutanix, ubuntu, rocky,
and konvoy.
List the InternalIP address of each node:
$ kubectl get nodes -o jsonpath='{.items[*].status.addresses[?
(@.type=="InternalIP")].address}'
On each node, append the new public key. Replace ~/.ssh/old-nkp-key with the path to the current
private key, and replace node-ip-address with the InternalIP address of the node.
$ cat ~/.ssh/new-nkp-key.pub | ssh -i ~/.ssh/old-nkp-key ${SSH_USER}@node-ip-address
 "cat >> ~/.ssh/authorized_keys"
Note:  The command connects to the InternalIP address of the node. If your nodes are in a private
subnet, run the command from a bastion host that can reach the virtual private cloud or virtual LAN, or
connect your local machine through a virtual private network. For more information, see Creating a
Bastion Host on page 679.
You can also distribute the new public key with a configuration management tool such as Ansible.
Nutanix Kubernetes Platform | Cluster Operations Management | 506

--- page 507 ---
7. Verify SSH access to a control plane or worker node using the new private key:
$ ssh -i ~/.ssh/new-nkp-key ${SSH_USER}@node-ip-address
Replace node-ip-address with the IP address of a cluster node. Successful login confirms that the
node accepts the new key.
8. (Optional) Remove the old public key from the authorized_keys file on each node:
Caution:  Remove only the old NKP public key. Leave all other keys in the authorized_keys file.
Disabling Automatic Onboarding During Cluster Upgrade
The upgrade process automatically enables the konnector-agent add-on on the workload cluster. If
you choose to disable it during an upgrade, you must manually modify the cluster configuration after the
upgrade manifest is generated.
About this task
Perform the following steps to disable automatic onboarding of clusters during an upgrade:
Procedure
1. Generate the upgrade manifest with --dry-run --output flag:
nkp cluster upgrade nutanix --cluster-name <CLUSTER_NAME> --dry-run --output yaml >
 upgrade-manifest.yaml
2. Edit the generated manifest and remove the konnectorAgent section from the cluster resource's add-
ons:
Remove or comment out the konnectorAgent section from addons:
   # konnectorAgent:
   #   credentials:
   #     secretRef:
   #       name: <CLUSTER_NAME>-pc-credentials-for-konnector-agent
3. Remove the konnectorAgent credentials secret from the manifest (if present):
Remove the Secret with the name:
<CLUSTER_NAME>-pc-credentials-for-konnector-agent
4. Apply the modified manifest:
kubectl apply -f upgrade-manifest.yaml
