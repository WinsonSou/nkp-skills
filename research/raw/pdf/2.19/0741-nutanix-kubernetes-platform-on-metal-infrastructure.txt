Nutanix Kubernetes Platform on Metal Infrastructure
Installing Nutanix Kubernetes Platform (NKP) on Metal servers deploys NKP directly on physical servers,
giving workloads direct access to compute, storage, network, and accelerator resources.
NKP Metal installation combines host discovery, operating system provisioning, cluster creation, and
host lifecycle management for Kubernetes clusters that run on physical servers. This deployment model
supports workloads that require low latency, high throughput, or dedicated hardware, such as artificial
intelligence, machine learning, GPU computing, and edge workloads.
Foundation Central discovers and images the physical servers. After imaging, each physical server
registers with the management cluster and becomes part of the available host inventory. Use an NKP
management cluster to manage the Metal host inventory and to use those physical servers for creating
workload clusters
The supported deployment model determines where the control plane and worker nodes run:
Full bare-metal workload cluster
The control plane nodes and worker nodes run on physical servers.

Mixed workload cluster
The control plane nodes and standard worker nodes run as virtual machines, and one or more

Workloads on physical servers use storage services that an Nutanix AOS cluster provides through the CSI

After installation, the management cluster maintains the desired cluster state and supports lifecycle

Creating a Nutanix CSI Volume Driver StorageClass for Mixed Workload Clusters
Create a dedicated StorageClass for workloads that run on the Metal node pool of a mixed workload
cluster.
About this task
When you create a mixed workload cluster, Nutanix Kubernetes Platform (NKP) creates a default
StorageClass for the virtual machine control plane and worker nodes. This default StorageClass uses
hypervisor-attached volumes and cannot provision storage for workloads that run on the Metal node pool,
because those Metal hosts have no hypervisor. Create a separate StorageClass for the Metal node pool,
and configure any workload on those nodes that requires a persistent volume to use this StorageClass
instead.
To create Nutanix CSI Volume Driver (CSI) StorageClass for mixed workload clusters, do the following:
Nutanix Kubernetes Platform | Custom Installation and Infrastructure Tools | 750

--- page 751 ---
Procedure
1. Create a YAML file that defines the StorageClass:
allowVolumeExpansion: true
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nutanix-volume-metal
parameters:
  csi.storage.k8s.io/controller-expand-secret-name: nutanix-csi-credentials
  csi.storage.k8s.io/controller-expand-secret-namespace: ntnx-system
  csi.storage.k8s.io/fstype: xfs
  csi.storage.k8s.io/node-publish-secret-name: nutanix-csi-credentials
  csi.storage.k8s.io/node-publish-secret-namespace: ntnx-system
  csi.storage.k8s.io/provisioner-secret-name: nutanix-csi-credentials
  csi.storage.k8s.io/provisioner-secret-namespace: ntnx-system
  fileSystem: ext4
  prismElementRef: <Prism Element UUID>
  storageContainer: <Storage Container name>
  storageType: NutanixVolumes
provisioner: csi.nutanix.com
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
Replace the prismElementRef and storageContainer placeholder values with the Prism Element
UUID and storage container name for your environment.
2. Apply the StorageClass to the mixed workload cluster:
kubectl apply -f storageclass-file-name.yaml
